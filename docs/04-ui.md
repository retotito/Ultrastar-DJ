# 04 — UI: windows, MVVM, design tokens, controls

## Windows

| Window | Class | Notes |
|---|---|---|
| DJ | `DjWindow` | Main window; closing it exits the app |
| Beamer 1 / 2 | `BeamerWindow` | Created by `DisplayService.Open(displayId, screen)`; fullscreen, borderless, on the chosen `Screen`; `Esc` closes; never has focus-stealing dialogs |

Both are plain Avalonia `Window`s in the same process. Beamers are **pure views**: their `BeamerViewModel`
subscribes to `PlaybackService` state and `GameSession` messages and holds only view state (countdown value,
score animation).

Screen selection uses `Screens.All`; persist the chosen screen by its bounds/name and fall back to the last
non-primary screen if it is gone.

## MVVM rules

- `CommunityToolkit.Mvvm`: `ObservableObject`, `[ObservableProperty]`, `[RelayCommand]`, `WeakReferenceMessenger`.
- ViewModels contain **no** Avalonia types (no `Brush`, `Bitmap`, `Window`). Views bind to primitive/record
  state; converters or custom controls turn it into visuals.
- Services (`PlaybackService`, `DisplayService`, `MediaChannel`s, `PlayersService`, …) are injected into
  ViewModels via constructor. Views are located by convention (`FooView` ↔ `FooViewModel`) using a small
  `ViewLocator`.
- Cross-VM communication goes through the messenger with **record** messages defined in `App/Messages/`.
  Do not let ViewModels reference each other.
- Anything that updates ≥ 20 Hz (levels, positions, ticks) bypasses `INotifyPropertyChanged` and drives a
  custom control directly (`InvalidateVisual`) — property-change storms are the #1 Avalonia perf mistake.
- Dialogs/popovers open via a `IDialogService`, never `new Window().Show()` inside a ViewModel.

The prototype's `app.css` becomes `Styles/Tokens.axaml` (dark) + `Styles/Tokens.Light.axaml`. Same names,
same values, so agents can map 1:1.

Rules (identical in spirit to the prototype):
- **Never** hardcode colours, sizes or font sizes in a view. Always `{DynamicResource ColorX}` / `{StaticResource SpaceN}`.
- New token → add to `Tokens.axaml` (and the light variant). Never define ad-hoc resources inside a view.
- Base theme: Avalonia **Fluent** with our colour resources overriding the palette. Component styles live in
  `Styles/Controls/*.axaml` (buttons, text fields, sliders, cards) — one file per control family.
- Icons: **Material Symbols** as a font (`Assets/Fonts/MaterialSymbolsOutlined.ttf`) via an `Icon` control
  taking the glyph name (`<c:Icon Name="mic_external_on"/>`). Same names as the prototype.

## Beamer view states

`BeamerView` switches on `PlaybackState`:

| State | Content |
|---|---|
| Idle | logo / "Ultrastar DJ" |
| Preview | background (cover blurred), title, artist, assigned player badges |
| Countdown | background + big 3 / 2 / 1 |
| Playing / Paused | `VideoSurface` (or image) + `GameOverlayControl` (lanes, lyrics, progress) + "PAUSED" overlay |
| Score | all players, animated scores, winner highlight |

Beamer reports `BeamerReady` once its `VideoSurface` is subscribed and the first layout pass is done, and
`CountdownDone` when its own 3-2-1 finishes.

## Things agents get wrong in Avalonia (read this)

- `x:Class` must match the code-behind class exactly (case-sensitive).
- Use `DynamicResource` for colours that change with theme; `StaticResource` for spacing/fonts.
- `Dispatcher.UIThread.Post` (not `Invoke`) from background threads; never block the UI thread waiting for mpv/PortAudio.
- `WriteableBitmap.Lock()` must be paired with dispose; copy the frame **inside** the lock and invalidate after.
- Avalonia `ListBox` virtualization requires a fixed-height item template and `VirtualizingStackPanel`.
- No WPF-only APIs (`Freezable`, `VisualBrush` tricks, `RenderTargetBitmap.Render` semantics differ). If an
  API is not in the Avalonia docs, it does not exist.
- Multi-window: each `Window` needs its own `DataContext`; do not share a ViewModel instance between beamers.
